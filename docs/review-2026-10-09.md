## What is good (keep)

- Milestone discipline: each of M1–M4 is a runnable slice with a written acceptance gate.
- Tests are real: backend `chat`/`workspace` packages were 100% on every JaCoCo dimension, the
  frontend enforces a 90% floor in `vitest.config.ts`, and the loop is proven with a fake
  `ChatModel` VCR.
- The manual loop in `ChatService` is right. In Spring AI 2.0.1 `OllamaChatModel` only resolves
  tool definitions and no longer executes tools (that moved to `ToolCallingAdvisor`), so
  `chatModel.stream(Prompt)` returns raw `tool_call` blocks as the loop expects.
- `ponytail:` comments record every deliberate shortcut with its upgrade path.
- Per-workspace SQLite with the registry outside the workspace dirs.

## Findings, ranked

### A. Confirmed defects

1. ✅ **The "fail-closed" executor was not fail-closed.** `ToolRegistry` put only `autoRun` tools
   in a `ToolCallbackResolver`, but `ChatService` handed `executeToolCalls` a `Prompt` whose
   options carried every callback. `DefaultToolCallingManager.executeToolCall` (2.0.1 sources
   lines 223–296) resolves from the prompt options first; the resolver is a fallback that is off
   by default (`DEFAULT_RESOLUTION_FALLBACK_ENABLED = false`). Any registered mutating tool would
   have run with no gate. The test asserted only `shouldNotBeNull()`. Also: an unresolvable name
   throws `IllegalStateException`; it does not yield a failed `tool_result`.
   Fix: claudius executes tools itself from an autoRun-only map; unknown or non-autoRun tools
   yield an error `tool_result`.

2. ✅ **A workspace named `.` or `.claudius` wiped every workspace on delete.** `sanitize` kept
   dots; `resolveDir(".")` normalized to the workspaces dir itself and passed the `startsWith`
   guard; `delete` then walked the whole workspaces dir including the registry DB. Only `..` was
   tested. Fix: reject dot-prefixed dirs; `resolveDir` requires a path strictly below the root.

3. ✅ **Client disconnect did not stop the loop.** `Flux.create` + `blockLast()` with nothing
   observing the sink's cancel: the backend kept calling Ollama and tools and persisted a turn
   nobody saw. Fix: a per-run stop signal (`Sinks.empty`) wired to `sink.onCancel` and
   `takeUntilOther` on the model stream.

4. ✅ **A model error left the UI stuck.** `sink.error` closed the SSE body without `done`; the
   frontend only cleared `streaming` from `onDone`/`catch`. Fix: `event: error` + `done` always;
   frontend finalizes in `finally`.

5. ✅ **The loop bound was an unhandled exception** (Spring's 40-calls-per-tool `THROW`). Fix:
   `claudius.chat.max-iterations` (default 25) ending the turn with an `error` chunk.

6. ✅ **Tool cards did not survive a reload.** `toolEvents` held pre-serialized JSON strings and
   was serialized again, persisting an array of strings; on reload every card was filtered out.
   Fix: `ToolInvocationDto` objects persisted once; REST returns `tools` as a list.

7. ✅ **Frontend stopped rendering live after one error.** `rafId` was never reset to 0 after an
   error or a workspace switch, so the next turn never scheduled a flush. Fix: reset in `catch`,
   cleanup and `finally`.

8. ✅ **Workspace name collision → 500.** `nameExists` checked the raw name, the dir came from the
   sanitized one ("a b" vs "ab"; "Foo" vs "foo" on macOS). Fix: a case-insensitive `dirExists`
   check → 400.

### B. Design seams that bite at M5/M6

9. ✅ (M6) **Tool context is dropped between turns.** Model context is rebuilt from `content` only; prior
   turns' tool calls/results are display-only. Wrong once `FileRead` exists. → M6.
10. ✅ **Transport plan was heavier than needed.** WS-per-run is replaced by SSE + REST commands
    keyed by a `runId` (`POST /api/chat/{runId}/cancel` now; `/answer` for approvals in M7).
11. ✅ **No per-workspace serialization.** A second chat on a busy workspace now returns 409.
12. **Provider coupling.** `ChatService.withTools` casts to `OllamaChatOptions`. → M11.
13. ✅ **Reasoning and text in one chunk were either/or.** Both are forwarded now.
14. ✅ **Dead code / unused deps** removed (`SessionStore.clear`, `toolEvent`, coroutines,
    reactor-kotlin, spring-security-test, kotlin-faker).
15. ✅ **No backend coverage gate.** `jacocoTestCoverageVerification` (90% line on `chat*` and
    `workspace*`) runs in `./gradlew check`.

## Verified claims (≥4 sources where web-verifiable)

- **Spring AI resolves tool callbacks from prompt options first; the resolver is an off-by-default
  fallback** — primary: `spring-ai-model-2.0.1-sources.jar` `DefaultToolCallingManager.java:84,
  223-296`; corroborated by spring-projects/spring-ai issue #6748 and the 2.1.0-SNAPSHOT javadoc.
- **Spring AI 2.0.x Ollama model has no internal tool loop** — `spring-ai-ollama-2.0.1-sources.jar`
  `OllamaChatModel.java:434,535`; spring.io blog 2026-06-15 "Composable tool calling".
- **Reactor: a `Flux.create` source must stop on cancel via `FluxSink.onCancel`/`onDispose`** —
  reactor-core 3.8.7 javadoc, reactor reference "Simple ways to create a Flux", Baeldung "Cancel
  an ongoing Flux", javathinking.com 2026-05-31.
- **Spring AI 2.0.1 is the current GA line** (2.0.0 GA 2026-06-12) — spring.io blog, GitHub
  releases, essamamdani.com 2026-08-14, javarubberduck.com 2026-06-29.
- **Vitest 5.0.3 is current** (5.0 released 2026-09-03); the project is on 3.2.7 — vitest.dev
  blog, GitHub releases, gitwatchman, releasebot. Upgrade is optional.
- **Not verified:** whether Ollama sends non-empty tool-call ids for the user's model (needs a
  live run). The backend writes `""` for a null id; the frontend matches by id and falls back to
  appending.
